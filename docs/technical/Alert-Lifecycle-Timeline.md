# Durable alert lifecycle timeline

This dashboard slice supplies retained alert transitions independently of the active inbox. Resolved cycles and refires remain addressable. Current alert actions keep their own current episode/revision readback; historical evidence never supplies mutation fences. Restart/failover collection and notification-delivery certification are outside this slice.

## Identity and timing

An event has an immutable canonical UUID. A cycle is the exact alert ID plus its episode ID when recorded; refiring creates a new alert ID and episode, never a continuation grouped only by rule ID. Legacy unknown episode/revision/name/value/recording metadata remains explicitly nullable and partial. Never borrow current rule/state/assignment/snooze data to fill old records. Exact selection binds event ID, alert ID, nullable episode ID and native event time.

Include actual fired, acknowledged and resolved state transitions, plus successful snoozed/unsnoozed/assigned/reassigned/unassigned operation receipts. Equal-state evaluations are not repeated firings. Snooze expiry is a deadline, not a fabricated lifecycle event. Recorded delivery suppression does not establish that a notification was sent or delivered.

Evaluation transitions use SQL/evaluator observation UTC as event time; acknowledgement, rule-disable resolution and ownership/snooze operations use their native repository apply time. Expose recording UTC separately where available. A current target revision is a read fence, not a fabricated historical sample revision or physical-host identity. Source target revision is nullable unless exact immutable source evidence establishes it.
